# visual-system

## Purpose

Convert the selected Creative World into an operable visual language that survives the real product architecture, dense information states, mobile constraints, consequential actions, and implementation needs.

Visual System is where exact visual candidates begin to be authored. It must not reopen Creative World exploration or alter the canonical information architecture to make the design easier. Motion is a first-class sub-system with its own runtime truth and browser-proof contract; it is not a final polish pass.

## When to use

- after a Creative World has been explicitly selected by a human from reviewed visual evidence;
- before production UI implementation is treated as visually approved;
- when typography, color, materials, iconography, components, motion, and responsive behavior need one coherent contract;
- when sparse art-direction proofs must be tested against long, code-heavy, evidence-heavy, error, streaming, tool, approval, and memory states;
- when AI work-state animation must remain tied to actual runtime events rather than generic loaders or simulated reasoning.

Do not use this stage to invent a new Creative World after selection.

## Inputs required

- human-selected Creative World artifact;
- frozen Product UX Architecture reference;
- frozen canonical fixture reference;
- selected-world constitution, derivation, guardrails, and anti-patterns;
- brand identity/brand-system constraints;
- required themes and accessibility constraints;
- canonical screen inventory;
- dense/edge-state stress requirements;
- formal Motion System artifact or authored Motion System V1 workstream.

## Operating principles

- Preserve the selected Creative World constitution rather than the pixels of an earlier proof.
- Typography provides hierarchy and reading speed; it must not force editorial pacing onto every long response.
- Semantic color frequency follows semantic event frequency.
- Consequence/authority styling stays rare and must not leak into ordinary conversation or navigation.
- Lineage graphics require real lineage.
- Components express information role and authority state; avoid one universal card style.
- Context remains subordinate to the primary conversation/workspace.
- Mobile simplifies infrastructure before content.
- Motion System is a source of truth, not a local component convention.
- Motion communicates real lifecycle changes and must not fabricate hidden reasoning, specialist activity, progress, or completion.
- Loading, working, reasoning-status, and execution-progress remain distinct product states.
- Reduced-motion equivalents are part of the authored system.
- Stress states are first-class proof surfaces, not post-hoc QA.
- Exact-browser proof may not delete canonical information to improve aesthetics.

## Workflow

1. Verify human-selected world authority and current architecture/fixture fingerprints.
2. Translate the selected constitution into brand-integration rules.
3. Author typography candidates and density behavior for short, long, code-heavy, and metadata-heavy content.
4. Author base and semantic color roles with consequence-leak rules.
5. Define surface/material hierarchy and semantic lineage behavior.
6. Define spacing/density modes for reading, working, evidence, and consequence states.
7. Define icon construction and semantic families.
8. Define component grammar across conversation, evidence, decision, memory, approval, code, tables, tools, and errors.
9. Define interaction and authority states.
10. Invoke `motion-system` to define event-backed work states, transition primitives, authority motion, execution progress, lineage, mobile behavior, and reduced-motion equivalents.
11. Bind Visual System components to the formal Motion System source of truth; do not invent component-local animation semantics.
12. Define responsive grammar and mobile simplification.
13. Build the required stress-state matrix.
14. Render exact-browser canonical screens and stress states.
15. Render exact-browser Motion System proof against the same canonical screens and runtime-state fixtures.
16. Review hierarchy, readability, consequence semantics, motion truthfulness, mobile behavior, accessibility, and brand distinctiveness.
17. Only after human inspection may motion/visual-system approval be recorded.

## Deliverables

- `ai-studio-os/visual-system@1` artifact;
- typography role/family/scale candidate;
- color + semantic color tokens;
- surface/material rules;
- spacing/density scale and modes;
- iconography construction rules;
- component grammar;
- interaction/authority state matrix;
- formal `ai-studio-os/motion-system@1` reference and consumption rules;
- responsive grammar;
- canonical-screen proof plan;
- dense/edge-state stress matrix;
- exact-browser visual proof;
- exact-browser motion proof;
- human review truth boundary.

## Review criteria

- selected Creative World constitution is preserved;
- conversation remains dominant;
- recommendation hierarchy improves judgment without slowing long responses;
- provenance is discoverable but not graph-like;
- authority/consequence states are unmistakable and rare;
- dense evidence and 10+ source lists remain efficient;
- code/tables/tool output remain technical and scannable;
- Project Memory scales beyond sparse mock data;
- Motion System uses event-backed status claims rather than AI theatre;
- approval/execution motion communicates a real authority transition;
- failure stops activity and makes recovery legible;
- mobile stays calm and does not restore desktop infrastructure;
- theme behavior preserves semantic meaning;
- focus, contrast, keyboard, and reduced-motion needs are defined;
- the system feels specifically like the product rather than generic premium SaaS;
- exact-browser proof keeps the canonical information intact.

## Failure modes

- selecting new worlds during Visual System work;
- treating previous proof colors/fonts as immutable because the world was selected;
- making every AI response large-serif editorial content;
- using lineage nodes or rails as decoration;
- spreading consequence color into normal navigation;
- using cards/shadows as the default hierarchy mechanism;
- hiding dense content to preserve a sparse aesthetic;
- using a spinner/orb to imply hidden chain-of-thought;
- inventing work statuses or agent activity to make a task feel busy;
- letting components define incompatible local loading/progress motion;
- building mobile as a compressed desktop;
- approving the visual system from token JSON without exact-browser visual and motion stress proof.

## Handoffs

- `product-ux-architecture` supplies the frozen product skeleton;
- Creative World / Hybrid selection supplies the selected constitution and authority;
- typography intelligence may supply production-ready type evidence and loading contracts;
- `motion-system` supplies the event-backed motion source of truth;
- `design` consumes the Visual System rather than recomputing it;
- `motion-designer` and motion engineering refine choreography within Motion System constraints;
- icon-system construction consumes the iconography construction rules;
- engineering consumes approved tokens/components and runtime-event adapters after human visual approval;
- review/QA verifies canonical, stress, and motion proof before final visual-system approval.
