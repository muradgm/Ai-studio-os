# motion-system

## Purpose

Turn a selected Creative World and authored Visual System candidate into a coherent motion language that explains real product state without simulating hidden reasoning or fake progress.

## When to use

- after a product interface has a human-selected Creative World;
- during Visual System development, before motion is treated as component polish;
- when an AI product exposes reading, working, evidence, specialist review, approval, execution, validation, lineage, or memory states;
- when runtime activity messages must remain truthful and event-backed;
- when desktop/mobile/reduced-motion behavior must share the same state semantics.

Do not use this skill to add ambient animation simply because a static interface feels quiet.

## Inputs required

- human-selected Creative World / Hybrid constitution;
- current Product UX Architecture and canonical fixture;
- current Visual System candidate;
- real or planned runtime event vocabulary;
- authority/governance states;
- execution/validation lifecycle;
- mobile and reduced-motion requirements.

## Operating principles

- Motion explains observable system state.
- Counterpoint owns reading/conversation motion.
- Decision Spine owns provenance/progression/history motion.
- Threshold owns consequence/authority motion only.
- Loading, working, reasoning-status, and execution-progress are different state classes.
- Named work stages require matching runtime events.
- Specialist participation must be factual.
- Completed marks require completed events.
- Unknown progress never uses percentage completion.
- Raw chain-of-thought and simulated agent dialogue are forbidden.
- Motion may reveal structured conclusions and lifecycle status, never hidden internal thought.
- Working copy changes at a calm cadence and only when the underlying stage changes.
- Failure stops motion; it does not increase spectacle.
- Consequence transitions may be more deliberate than ordinary UI transitions.
- Mobile is quieter than desktop.
- Reduced motion preserves state meaning and hierarchy.

## Workflow

1. Bind motion to the selected Creative World and current Visual System candidate.
2. Define the four runtime state classes.
3. Define timing hierarchy and cadence.
4. Define an explicit runtime event vocabulary for every status claim.
5. Define motion primitives for submission, understanding, context, evidence, Council review, strategy comparison, long work, answer reveal, verification, approval, execution, validation, success/failure, lineage, memory, panels, mobile, and reduced motion.
6. Bind primitives to the frozen eight canonical screens.
7. Define real-runtime-state proof scenarios.
8. Validate that every state-claiming primitive requires runtime evidence.
9. Run exact Chromium motion proof.
10. Run reduced-motion equivalence proof.
11. Independently review for AI theatre, false progress, excessive motion, and authority leakage.
12. Keep human motion/visual approval false until explicit review.

## Deliverables

- `ai-studio-os/motion-system@1` artifact;
- event vocabulary and truth policy;
- four work-state classes;
- timing/cadence tokens;
- screen-bound motion primitives;
- canonical-screen integration map;
- real-runtime-state proof scenarios;
- reduced-motion contract;
- exact-browser proof manifest and motion clips/frames;
- production-adapter status;
- explicit approval truth flags.

## Review criteria

- motion explains a real state or relationship;
- ordinary conversation remains calm;
- work messages correspond to actual lifecycle events;
- long-running work communicates meaningful state without status churn;
- evidence acquisition makes provenance clearer without becoming a graph;
- specialist review communicates coordination without agent theatre;
- structured answers reveal by meaningful section rather than excessive typewriter animation;
- approval is the strongest authority transition;
- execution progress corresponds to actual operations;
- failure produces controlled stillness and recovery actions;
- lineage and memory animations represent real temporal relationships;
- mobile uses fewer simultaneous motions than desktop;
- reduced-motion users receive equivalent state information;
- no false percentages, fake thoughts, fake conversations, or celebratory noise appear.

## Failure modes

- using one spinner/pulsing-dot treatment for every state;
- inventing runtime stages to reassure the user;
- changing work copy every second;
- presenting model chain-of-thought as product transparency;
- showing agent avatars talking to one another;
- animating strategy scores before evaluation completes;
- drawing lineage connectors without real provenance;
- making consequence red or Threshold motion permanent product chrome;
- turning execution success into celebration;
- reproducing desktop motion complexity on mobile;
- omitting a reduced-motion equivalent.

## Handoffs

- `product-ux-architecture` supplies canonical screens and interaction hierarchy;
- the selected Creative World supplies Hybrid responsibility boundaries;
- `visual-system` supplies typography, color, surface, component, density, and responsive grammar;
- runtime/event adapters supply production truth for work-state claims;
- `motion-designer` may refine choreography within this contract;
- `motion-review`, accessibility, performance, and responsive reviews validate production fitness;
- engineering consumes event/status contracts without exposing hidden chain-of-thought.
