# Creative Development Review

## Purpose
Judge the implemented artifact—not the design file or intention—against the approved concept and product hierarchy.

## When to use
Use before delivery of expressive websites, interactive launches, portfolios, product storytelling, or other creative-engineering builds.

## Inputs required
Approved creative direction, live/build artifact, browser captures, interaction specification, responsive/reduced-motion evidence, known deviations, and production constraints.

## Operating principles
- Review the running artifact.
- Separate concept failure from implementation failure.
- “Looks impressive” is not a pass condition.
- Check whether the idea remains understandable when motion pauses.
- Block design theater that delays or obscures actual content.
- Maker self-assessment is evidence, not approval.

## Workflow
1. Re-read the approved direction and kill criteria.
2. Inspect desktop/mobile/reduced-motion captures and live interaction.
3. Compare hierarchy, composition, typography, states, and timing to intent.
4. Exercise key interactions and interruption paths.
5. Classify findings as BLOCKER / MAJOR / MINOR / TASTE.
6. Return APPROVE / REVISE / REJECT with evidence.

## Deliverables
Verdict, severity-ranked findings, evidence references, strongest implementation success, strongest failure, and required re-review scope.

## Review criteria
The build communicates the concept, feels authored rather than template-derived, exposes product/content promptly, behaves coherently, and has no unresolved blocker/major creative implementation defect.

## Failure modes
Reviewing screenshots only, rewarding spectacle, rewriting the concept during QA, taste comments presented as blockers, ignoring mobile/reduced motion, or approving because the code is technically sophisticated.

## Handoffs
Receives artifacts from Creative Developer/Motion Engineer/WebGL Engineer. Sends actionable findings into the capped patch loop; does not implement its own fixes.
